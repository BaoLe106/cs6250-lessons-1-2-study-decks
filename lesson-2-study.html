Transport above IP

IP reaches a host; transport provides a logical connection between applications.

Transport receives an application message, adds its header to make a segment, and hands it to IP. It hides heterogeneous access networks and IP’s best-effort behavior from application programmers.

Two common choices: UDP offers a minimal service; TCP adds reliability and rate-control primitives.

Why multiplex?

One IP address must serve many processes at once.

The network layer cannot decide whether an arriving packet belongs to the browser, music app, or game. Transport uses ports and sockets.

Multiplexing: collect data from many sockets, label it, and send segments. Demultiplexing: inspect labels and deliver each segment to the correct socket.

Connectionless vs connection-oriented demux

UDP identifies a local destination; TCP identifies a connection.

UDP · connectionless

Socket identity: 2-tuple

destination IP
destination port

Segments from different sources addressed to the same destination port go to the same socket.

TCP · connection-oriented

Socket identity: 4-tuple

source IP + source port
destination IP + destination port

A server can distinguish many simultaneous clients even when all connect to port 80.

Persistent HTTP: reuse a TCP connection. Non-persistent HTTP: repeatedly create/close connections—costly for a busy server.

A word about UDP

UDP removes mechanisms so the application keeps control.

It is connectionless: no handshake, no TCP-style retransmission, and no built-in congestion control. Send immediately when the application hands over data.

Use when: delay or application control matters more than recovering every packet—e.g., real-time media; DNS commonly uses UDP.

Reliable transmission

TCP delivers the byte stream in order, without loss or corruption.

Sequence numbers identify data; ACKs report receipt; timers trigger retransmission when an ACK is absent. This is ARQ.

Timeout trade-off: too short → needless retransmissions; too long → needless delay. RTT estimation informs the timeout.

Stop-and-wait

Send one, wait for ACK. Simple, but poor utilization.

Sliding window

Allow up to N unacknowledged packets; buffers and sequence numbers become necessary.

Go-back-N

Receiver discards later out-of-order packets; sender repeats from loss onward.

Selective ACK

Buffer/ack good out-of-order data; retransmit only missing data.

Dynamic problem: flows arrive and depart, so control must continually adapt.

E2E vs network-assisted

TCP historically infers congestion at endpoints.

Network-assisted

routers explicitly signal congestion (modern examples include ECN/QCN).

End-to-end

hosts infer from observed behavior; aligns with the end-to-end principle.

TCP chose E2E: endpoints can implement it without requiring every router to participate.

Two classic signals

Rising RTT: queues build, but delay is noisy.

Loss: congested routers drop packets; TCP already detects loss for reliability.

Loss can have non-congestion causes, but early TCP primarily used it as congestion evidence.

TCP sender rate

Probe for capacity with cwnd, then back off on congestion.

The congestion window caps bytes in flight due to network conditions. ACKs act as probes: successful delivery allows more release.

Actual sending limit: the smaller window. TCP cannot outrun either the receiver or the path.

TCP congestion control · AIMD

Increase gently; reduce sharply.

Additive increase: roughly +1 packet per RTT (incremented per ACK in practice). Multiplicative decrease: on loss, cut cwnd in half.

Reno: triple duplicate ACK = milder loss → halve cwnd. Timeout = more severe → reset toward initial window.

Slow start

From a cold start, exponential growth reaches a useful rate quickly.

Start near 1 packet. Each ACK adds one packet of window, so a full RTT approximately doubles cwnd: 1 → 2 → 4 → 8 …

At ssthresh: move into additive increase. After a timeout, slow start again avoids dumping a large old window into an uncertain network.

TCP fairness

AIMD tends toward equal sharing—under ideal assumptions.

For k connections with the same RTT sharing bottleneck capacity R, the target is roughly R/k each. Increase moves toward full use; shared loss makes all reduce, repeatedly steering toward fairness.

Important: fairness is a policy concept, not a universal fact.
RTT bias

Shorter RTT sees ACKs more often and can increase cwnd faster.

Parallel connections

An app opening many TCP flows can capture more than a fair one-flow share.

Modern networks · TCP CUBIC

CUBIC grows fast far from the last loss point and carefully near it.

Reno can underuse high-bandwidth, high-delay paths. After loss at Wmax, CUBIC reduces then uses a cubic, time-based growth curve.

W(t) = C(t − K)³ + Wmax
Why time-based? CUBIC is less RTT-biased than ACK-clocked Reno and targets high bandwidth-delay-product networks.

TCP throughput + optional datacenter TCP

Loss and RTT bound classic TCP throughput.

Reno’s sawtooth means its simplified throughput model is proportional to 1 / (RTT × √p), where p is loss probability. More loss or more RTT means less throughput.

Model caveat: receiver windows, timeouts, and other real details lower the constant in practice.

Why datacenters differ

Many short, delay-sensitive flows; one operator can deploy coordinated changes.

One-sentence model

TCP turns IP best effort into a reliable, rate-adaptive app service by using endpoint feedback: sequence/ACKs, windows, and controlled probing.
